## 2. Классификация

### A. Реальные bugs текущей beta
- BUG-01, BUG-02, BUG-03
- NODE-01, NODE-02, NODE-03, NODE-05, NODE-06

### B. Архитектурные проблемы
- **Смешение UI-вывода и machine-readable return-канала** (первопричина BUG-01/BUG-02) — не локальный баг одной функции, а отсутствие системного соглашения в `lib/ui/output.sh` о разделении каналов.
- **Отсутствие timeout-контракта** для внешних операций (API-вызовы, SSH-выполнение) — NODE-01/NODE-02, системно, не только в Remote Node.
- **CREATE-only модель Remote Node registration** без reconcile/upsert-слоя (NODE-07) — структурное свойство `panel_node_register()`, требует архитектурного решения, а не патча.
- **Trap-стратегия ограничена `RETURN`**, не покрывает прерывания — влияет на cleanup-гарантии в целом, не только для Remote Node.

### C. Code smells
- NODE-06 (дублирующая интерполяция `${extra_pkgs}`) — не влияет на Remote Node функционально, косметический дефект в shared-коде.
- Несогласованность между `remote_install_deps()`-дефолтами и реальным стеком вызывающей стороны (NODE-05) — можно классифицировать и как smell («молчаливый дефолт»), и как bug; отнесён к bug выше, т.к. имеет наблюдаемый эффект (лишние пакеты).

### D. Сознательные ограничения/поведение (задокументированы в коде, не являются скрытыми багами)
- Неидемпотентность Remote Node registration — явно предупреждается пользователю (`install.sh:28`: «Повторный запуск создаст новую ноду/хост в Panel»). Это **NODE-07**, зафиксирован как INFO, а не bug.
- Отсутствие rollback удалённого состояния (Docker-контейнеры, ufw-правила, скопированные файлы) при partial-failure после начала SSH-деплоя — согласуется с типичным поведением infra-деплой-тулов, не помечено как баг.
- Soft-check порта 2222 (`ss -tln | grep :2222`) намеренно не фатален — гоночное условие по таймингу принято как есть.

## 3. Что НЕ нужно чинить отдельными патчами перед рефакторингом

Эти проблемы либо (а) являются прямым следствием архитектурного решения, которое рефакторинг обязан пересмотреть целиком, либо (б) их патч-фикс без изменения архитектуры создаст временное решение, которое придётся выбросить:

- **BUG-01, BUG-02** — их корень (смешение UI/data-каналов в stdout) должен решаться на уровне архитектуры возврата данных из функций (структурированный контракт), а не точечным патчем `panel_node_register()`. Локальный патч (например, `2>&1`-перенаправление `ok/warn` в stderr только в этой функции) технически закрыл бы находки, но не устранил бы системный риск повторения паттерна в новом коде — это принадлежит рефакторингу error/output-контракта.
- **NODE-07 (CREATE-only)** — переход к reconcile-модели (раздел 5) — это структурное изменение `panel_node_register()`/`panel_setup_api()`, а не патч поверх текущей POST-only логики. Патчить «добавить проверку существования» точечно, не решив вопрос reconcile/repair целиком, породит промежуточную непоследовательную модель.
- **NODE-05** (дефолт web_server) — правильное решение — сделать параметр обязательным по всей кодовой базе (все call sites `remote_install_deps`), это затрагивает более одного вызова и логично сделать в рамках общего пересмотра сигнатур bootstrap-функций при рефакторинге.
- **NODE-06** — эффект для Remote Node нулевой; чинить в отрыве от остального `lib/common/ssh.sh` нет смысла.

## 4. Что обязательно должно быть исправлено/зафиксировано ДО начала рефакторинга

Критерий включения сюда: проблема создаёт **риск во время самого процесса рефакторинга** (например, маскирует реальные ошибки, из-за чего рефакторинг будет тестироваться на неверных сигналах) или представляет собой **активный security/availability риск в проде прямо сейчас**, независимо от архитектурной модели, которая придёт ей на смену.

- **BUG-02 (CRITICAL)** — false-negative детекция ошибок должна быть зафиксирована (не обязательно «архитектурно исправлена», но минимум **задокументирована как known-broken** и, желательно, временно пропатчена на уровне caller — проверка `$?` вместо `[ -z ]`) ДО того, как на неё будут опираться при тестировании нового reconcile-поведения в рефакторинге. Иначе новый код будет тестироваться поверх той же слепой зоны.
- **NODE-01, NODE-02 (HIGH, availability)** — отсутствие timeout — это активный операционный риск (зависание процесса) уже сегодня, не связанный с тем, какая архитектура registration придёт на смену. Достаточно минимальной фиксации (добавить `--max-time`/`timeout`-обёртку) независимо от даты рефакторинга.
- **NODE-03 (HIGH, security)** — world-readable SECRET_KEY — активный риск в проде прямо сейчас, не зависит от архитектуры registration-флоу. Минимальная фиксация (`chmod 600`) не конфликтует ни с одним будущим архитектурным решением.

Остальные (BUG-01, BUG-03, NODE-04, NODE-05, NODE-06, NODE-07) — допустимо оставить до рефакторинга (раздел 3 и/или раздел «DEFERRED» в п.8), т.к. либо не создают риска именно во время процесса рефакторинга, либо будут естественно устранены при пересмотре архитектуры.

## 5. Remote Node lifecycle — целевое поведение

### 5.1 Текущее состояние (подтверждено аудитом)
- `panel_node_register()` — **чистый CREATE**: `POST /api/config-profiles`, `POST /api/nodes`, `POST /api/hosts` без предварительной проверки существования (NODE-07).
- Единственный существующий пример upsert-паттерна в кодовой базе — `panel_setup_api()` (`lib/panel/api.sh:50-53`), где для `Default-Profile` явно реализованы `GET` + `select(.name==...)` + `DELETE` перед созданием нового. Этот паттерн **не переиспользован** в `panel_node_register()`.
- Health-check (`panel_node_wait_connected()`) существует, но сегодня практически недостижим в исправном виде из-за BUG-01 (испорченный TOKEN).
- Repair/reinstall/reconcile-операций как отдельных сущностей в коде не существует — есть только «запусти установку заново», что означает дублирование ресурсов.

### 5.2 Зафиксированное целевое поведение (по итогам обсуждения в задании)

> Повторная установка существующей ноды должна приводить к **reconcile/reinstall**, а не создавать новую Node/Host/Config Profile без необходимости.

Формализация для рефакторинга:

1. **Identity-ключ ноды** должен быть зафиксирован явно (кандидат по текущему коду: `SELFSTEAL_DOMAIN`, т.к. это единственное устойчивое пользовательское значение, используемое сегодня и в имени config-profile/node, `RemoteNode-${SELFSTEAL_DOMAIN}`, и в Host `sni`/`address`). Архитектура должна явно решить, является ли `SELFSTEAL_DOMAIN` каноническим identity-ключом, или нужен отдельный стабильный идентификатор.
2. **Lookup-before-create**: перед `POST /api/nodes` — `GET`-проверка существования Node/Host/Config-profile с этим identity-ключом (по аналогии с существующим паттерном в `panel/api.sh:50-53`, но обобщённым на все три сущности, не только config-profile).
3. **Три исхода lookup**, а не два (create/fail):
   - **Not found** → CREATE (текущее поведение, как единственный случай).
   - **Found + healthy** (Node существует и `isConnected=true`) → **no-op / reconcile без пересоздания** (обновить только то, что реально изменилось — например, IP ноды, конфигурацию inbound, — без пересоздания UUID-based сущностей).
   - **Found + unhealthy/incomplete** (Node существует, но не подключена, либо Host/Squad отсутствуют/рассинхронизированы — то есть ровно тот класс состояний, который сегодня порождает BUG-03) → **repair-путь**: доделать недостающие шаги (создать отсутствующий Host, обновить Squad) без пересоздания уже существующих сущностей.
4. **Reinstall как отдельный явный режим**, отличный от reconcile: пользователь должен иметь возможность запросить полное пересоздание (удалить старые Node/Host/Config-profile и создать заново) как осознанное действие, а не как побочный эффект повторного запуска той же команды.
5. **Health-check должен быть частью reconcile-цикла**, а не только post-create-шагом: reconcile обязан уметь проверить текущее состояние подключения существующей ноды, а не только вновь созданной.
6. **Failure recovery**: если reconcile прерывается на середине (например, Host починен, но Squad — нет), повторный запуск должен снова определить это через lookup и доделать оставшееся — то есть reconcile должен быть **сам идемпотентен** (safe to re-run), а не просто заменить одну неидемпотентную операцию на другую.

### 5.3 Прямая связь с уже найденными багами
Переход к reconcile-модели не отменяет необходимость чинить BUG-01/BUG-02/BUG-03 — наоборот, требует их решения как предпосылки:
- Reconcile невозможен без надёжного machine-readable TOKEN/NODE_UUID (BUG-01 должен быть решён).
- Reconcile невозможен без надёжной детекции успеха/неуспеха у caller'а (BUG-02 должен быть решён).
- BUG-03 (частичный Host/Squad failure) по сути **является** тем самым состоянием "Found + unhealthy/incomplete" из п.5.2.3 — то есть текущий баг становится штатным, ожидаемым состоянием, которое reconcile обязан уметь чинить, а не игнорировать через `warn`.

## 6. Требования к рефакторингу

### Functional requirements
- Remote Node lifecycle должен поддерживать: create, reconcile (idempotent re-run), explicit reinstall, health-check как часть reconcile — согласно разделу 5.2.
- Identity-ключ ноды должен быть явно определён и задокументирован в коде (не подразумеваться неявно через имя config-profile).

### Architectural requirements
- Единое соглашение о разделении UI-вывода (stderr) и machine-readable return-значений (stdout или структурированный канал) для всех функций, вызываемых через `$(...)` — не только для `panel_node_register()`.
- Явный timeout-контракт по умолчанию для всех внешних вызовов: HTTP (curl `--max-time`), SSH (execution-level, не только connect-level).
- Trap-стратегия должна покрывать не только `RETURN`, но и прерывания процесса (`EXIT`/`INT`/`TERM`) там, где создаётся persistent state (staging-файлы, remote-артефакты).

### Error-handling requirements
- Caller обязан определять успех/неуспех операции по коду возврата (`$?`), а не по эвристикам над содержимым stdout (прямое следствие BUG-02).
- Частичный успех (напр. Node создана, Host — нет) должен быть представлен как отдельное, различимое состояние в контракте функции — не маскироваться под полный успех (BUG-03) и не молча приводить к падению всего процесса.

### Idempotency requirements
- Повторный запуск create-операции для уже существующей ноды не должен создавать дубликаты сущностей на стороне Panel (см. раздел 5.2 целиком).
- Reconcile-операция должна быть safe to re-run (идемпотентна сама по себе), включая её собственные частичные сбои.

### Security requirements
- Файлы, содержащие секреты (`SECRET_KEY` и аналогичные), должны создаваться с restrictive permissions (`chmod 600` или эквивалент) как обязательный шаг генерации — и локально, и после переноса на remote-хост (NODE-03).
- Передача паролей внешним командам (`sshpass`) не должна проходить через argv/cmdline — использовать file descriptor/env-based механизм (NODE-04). Это требование распространяется на весь SSH-слой (`lib/common/ssh.sh`, `lib/migrate.sh`, `lib/telemt/migrate.sh`), не только на Remote Node.

### Cleanup/rollback requirements
- Cleanup-механизм должен явно определять: что откатывается локально (Panel-хост staging) и что — на удалённой стороне (remote node), и это должно быть осознанным архитектурным решением, а не непроверенным умолчанием (см. Untested area из предыдущего аудита: поведение при partial SSH-деплое-failure задокументировано только частично).
- Cleanup должен переживать прерывание процесса, не только штатный `return` (см. NODE-02).

### Testing requirements
- `[ТРЕБУЕТ ВХОДНЫХ ДАННЫХ]` — конкретные testing requirements для рефакторинга (unit/integration/mock Panel API стратегия) не обсуждались в рамках доступной мне сессии. Рекомендую как минимум: воспроизводимый mock-harness для `panel_api()` (аналогичный использованному в этом аудите) должен стать частью репозитория/CI, а не одноразовым артефактом аудита — иначе регрессии по BUG-01/02/03-классу не будут пойманы автоматически.
